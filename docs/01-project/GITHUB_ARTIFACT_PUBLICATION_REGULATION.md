# Регламент единой публикации и проверки артефактов в GitHub

## 1. Назначение и область применения

Механизм `GITHUB-ARTIFACT-PUBLISH-001 v1.0` стандартизирует публикацию текстовых и бинарных артефактов: XLSX, DOCX, PDF, PPTX, CSV, JSON, Markdown, PNG/JPG, ZIP и иных файлов. Регламент не изменяет предметные данные проектов; он управляет доставкой, идентификацией, контролем целостности, merge и post-merge verification.

## 2. Принципы управления

1. GitHub является единым источником истины.
2. Каждая публикация идентифицируется Issue, рабочей веткой, PR и exact commit SHA.
3. Пользователь выполняет одну короткую команду; технические детали инкапсулированы.
4. Merge запрещён до письменного Owner/Merge Gate.
5. Закрытие Issue разрешено только после проверки результата в `main`.
6. Ошибка проверки имеет приоритет над автоматическим продолжением операции.

## 3. Архитектура

| Компонент | Ответственность |
|---|---|
| `publish-artifact.sh` | обнаружение файла, первичная валидация, ветка, commit, push, draft PR, exact-SHA download, byte comparison |
| `verify-artifact.sh` | независимая проверка наличия, размера, SHA-256, Git blob SHA, формата и состава пакета |
| `complete-artifact-publication.sh` | контроль Merge Gate и head SHA, ready, merge, post-merge verification, закрытие Issue |
| `install-macos.sh` | однократная установка коротких команд в `$HOME/bin` и PATH |
| `configs/issue-N.conf` | декларативная карточка конкретной публикации |
| `lib/common.sh` | единые проверки, сообщения и служебные функции |

## 4. Карточка публикации

Обязательные поля: `REPOSITORY`, `ISSUE_NUMBER`, `BASE_BRANCH`, `WORK_BRANCH`, `SOURCE_PATTERN`, `TARGET_PATH`, `FILE_TYPE`, `EXPECTED_FILES`, `MERGE_ALLOWED`, `CLOSE_ISSUE_ALLOWED`. Для Merge Gate применяются `PR_NUMBER` и `APPROVED_HEAD_SHA`.

Карточку создаёт и изменяет агент. Пользователь не редактирует её вручную.

## 5. Контроль целостности

Проверка включает:

- наличие и ненулевой размер;
- форматную сигнатуру или структуру;
- SHA-256;
- Git blob SHA по алгоритму Git `blob <size>\0<content>`;
- наличие всех файлов, перечисленных в `EXPECTED_FILES`;
- скачивание из exact commit SHA;
- побайтовое сравнение локального и опубликованного файла.

Office Open XML и ZIP проверяются как ZIP-контейнеры. PDF проверяется по заголовку `%PDF-` и завершающему маркеру `%%EOF`. PNG/JPEG проверяются по magic bytes. JSON проходит синтаксический разбор. Текстовые форматы проверяются как непустой текст.

Для бинарных файлов exact-SHA verification выполняется через неизменяемый Git blob SHA с base64-декодированием. Это исключает преобразование бинарного содержимого HTTP-клиентом и обеспечивает одинаковый маршрут для текстовых и бинарных файлов.

## 6. Конечный автомат состояний

`LOCAL_APPROVED → VALIDATED → COMMITTED → PUSHED → DRAFT_PR → HEAD_VERIFIED → OWNER_GATE → MERGED → MAIN_VERIFIED → ISSUE_COMPLETED`.

Переход вперёд разрешён только при PASS текущего контроля. Любой отрицательный результат переводит операцию в `BLOCKED` без merge и без закрытия Issue.

## 7. Пользовательский интерфейс

Основной вывод ограничен итогом и одним действием:

```text
PUBLICATION_RESULT=PASS
```

или

```text
PUBLICATION_RESULT=BLOCKED
ПРОБЛЕМА: ...
ЧТО СДЕЛАТЬ: ...
```

Полный журнал записывается в `${TMPDIR:-/tmp}/github-artifacts-logs/`.

## 8. Безопасность

Программы не читают и не печатают GitHub token. Авторизация выполняется штатным `gh auth`. Скрипты не применяют `git add -A` и не продолжают работу при грязном рабочем дереве. Merge и закрытие Issue разделены с публикацией и защищены декларативными флагами.

Установщик не меняет права файлов внутри рабочей копии репозитория. Короткие команды создаются как обычные исполняемые wrapper-файлы в `$HOME/bin`, вызывающие целевые программы через `bash`. Перед созданием wrapper удаляется прежний файл или символическая ссылка, что исключает рекурсивный самовызов.

## 9. Совместимость macOS

Целевая среда — штатный Bash 3.2 в macOS. Код не должен использовать возможности Bash 4+, включая `mapfile` и преобразование регистра `${var,,}`. Объявление локальных переменных и вычисление зависимых значений выполняются раздельно, чтобы режим `set -u` не приводил к ошибкам необъявленной переменной.

Программа поддерживает два расположения локальной копии:

- рабочая копия пользователя;
- управляемый клон в `$HOME/GitHub/<repository>`.

Если рабочая ветка уже существует на `origin`, программа создаёт локальную tracking-ветку вместо новой несвязанной ветки.

## 10. Испытания и приёмка

Автоматизированный набор `tests/run-tests.sh` покрывает 15 требований Issue #100: Markdown, XLSX, PDF, PNG, ZIP; отсутствие и повреждение файла; отсутствие авторизации; отсутствие локального репозитория и ветки; грязное дерево; неоднозначный выбор файла; несовпадение SHA; сохранение draft до gate; блокировку при ошибке post-merge verification.

Натурные испытания на macOS от 5 августа 2026 года:

| Испытание | Результат |
|---|---|

| оба испытательных PR остаются draft и содержат по одному целевому файлу | PASS |

В ходе натурных испытаний выявлены и исправлены следующие дефекты:

1. отсутствие executable bit у файлов, созданных GitHub Contents API;
2. изменение прав файлов рабочей копии установщиком;
3. перезапись через прежнюю символическую ссылку и рекурсивный самовызов;
4. отсутствие видимого прогресса установщика;
5. несовместимость `mapfile` и `${var,,}` со штатным Bash 3.2;
6. объявление зависимых локальных переменных одной командой при `set -u`;
7. создание новой локальной ветки при уже существующей remote tracking branch;
8. ненадёжная raw-загрузка бинарного ZIP через Contents API.

До финальной приёмки остаются:

1. повторный автоматизированный прогон тестов текущей версии;
2. независимая проверка опубликованных Markdown и ZIP через `verify-github-artifact`;
3. письменный Owner/Merge Gate;
4. post-merge verification в `main`;
5. выпуск release `GITHUB-ARTIFACT-PUBLISH-001 v1.0`.

## 11. Версионирование

Первый стабильный выпуск: `GITHUB-ARTIFACT-PUBLISH-001 v1.0`. Изменения интерфейса карточек или контрольных алгоритмов требуют новой версии и записи в release notes.
