# Регламент единой публикации и проверки артефактов в GitHub

## 1. Назначение и область применения

Механизм `GITHUB-ARTIFACT-PUBLISH-001 v1.0` стандартизирует публикацию текстовых и бинарных артефактов: XLSX, DOCX, PDF, PPTX, CSV, JSON, Markdown, PNG/JPG, ZIP и иных файлов. Регламент не изменяет предметные данные проектов; он управляет доставкой, идентификацией, контролем целостности, merge и post-merge verification.

## 2. Принципы управления

1. GitHub является единым источником истины.
2. Каждая публикация идентифицируется Issue, рабочей веткой, PR и exact commit SHA.
3. Пользователь выполняет одну короткую команду; технические детали инкапсулированы.
4. Merge запрещён до письменного Owner/Merge Gate.
5. Закрытие Issue разрешено только после проверки результата в `main` и публикации обязательного release.
6. Ошибка проверки имеет приоритет над автоматическим продолжением операции.
7. Пользователь не обязан помнить номера служебных Issues, команды, шлюзы или необходимость Release Gate: состояние жизненного цикла ведёт ChatGPT.
8. После каждой полной или частичной итерации выполняется обязательный `PROCESS IMPROVEMENT REVIEW`.

## 3. Архитектура

| Компонент | Ответственность |
|---|---|
| `publish-artifact.sh` | обнаружение файла, первичная валидация, ветка, commit, push, draft PR, exact-SHA download, byte comparison |
| `verify-artifact.sh` | независимая проверка наличия, размера, SHA-256, Git blob SHA, формата и состава пакета |
| `complete-artifact-publication.sh` | контроль Merge Gate и head SHA, ready, merge, post-merge verification, закрытие Issue |
| `install-macos.sh` | однократная установка коротких команд в `$HOME/bin` и PATH |
| `configs/issue-N.conf` | декларативная карточка конкретной публикации |
| `lib/common.sh` | единые проверки, сообщения и служебные функции |
| `GITHUB_ARTIFACT_PROCESS_IMPROVEMENT_REGISTER.md` | реестр отклонений, решений и эффективности улучшений |
| `GITHUB_PROCESS_IMPROVEMENT_REVIEW_TEMPLATE.md` | обязательный шаблон анализа каждой итерации |

## 4. Карточка публикации

Обязательные поля: `REPOSITORY`, `ISSUE_NUMBER`, `BASE_BRANCH`, `WORK_BRANCH`, `SOURCE_PATTERN`, `TARGET_PATH`, `FILE_TYPE`, `EXPECTED_FILES`, `MERGE_ALLOWED`, `CLOSE_ISSUE_ALLOWED`. Для Merge Gate применяются `PR_NUMBER` и `APPROVED_HEAD_SHA`.

Карточку создаёт и изменяет агент. Пользователь не редактирует её вручную.

## 5. Контроль целостности

Проверка включает:

- наличие и ненулевой размер;
- форматную сигнатуру или структуру;
- SHA-256;
- Git blob SHA по алгоритму Git `blob <size>\0<content>`;
- наличие всех файлов, перечисленных в `EXPECTED_FILES`;
- скачивание из exact commit SHA;
- побайтовое сравнение локального и опубликованного файла.

Office Open XML и ZIP проверяются как ZIP-контейнеры. PDF проверяется по заголовку `%PDF-` и завершающему маркеру `%%EOF`. PNG/JPEG проверяются по magic bytes. JSON проходит синтаксический разбор. Текстовые форматы проверяются как непустой текст.

Для бинарных файлов exact-SHA verification выполняется через неизменяемый Git blob SHA с base64-декодированием. Это исключает преобразование бинарного содержимого HTTP-клиентом и обеспечивает одинаковый маршрут для текстовых и бинарных файлов.

## 6. Конечный автомат состояний

`LOCAL_APPROVED → VALIDATED → COMMITTED → PUSHED → DRAFT_PR → HEAD_VERIFIED → OWNER_GATE → MERGED → MAIN_VERIFIED → RELEASED → PROCESS_REVIEWED → ISSUE_COMPLETED`.

Переход вперёд разрешён только при PASS текущего контроля. Любой отрицательный результат переводит операцию в `BLOCKED` без merge и без окончательного закрытия Issue.

## 7. Пользовательский интерфейс

Основной вывод ограничен итогом и одним действием:

```text
PUBLICATION_RESULT=PASS
```

или

```text
PUBLICATION_RESULT=BLOCKED
ПРОБЛЕМА: ...
ЧТО СДЕЛАТЬ: ...
```

Полный журнал записывается в `${TMPDIR:-/tmp}/github-artifacts-logs/`.

Пользователь выполняет только управленческие решения и те короткие команды Terminal, которые ChatGPT не может выполнить через подключённые системы. ChatGPT обязан сам определить момент такого действия, подготовить полностью готовую команду и затем проверить результат.

## 8. Безопасность

Программы не читают и не печатают GitHub token. Авторизация выполняется штатным `gh auth`. Скрипты не применяют `git add -A` и не продолжают работу при грязном рабочем дереве. Merge и закрытие Issue разделены с публикацией и защищены декларативными флагами.

Установщик не меняет права файлов внутри рабочей копии репозитория. Короткие команды создаются как обычные исполняемые wrapper-файлы в `$HOME/bin`, вызывающие целевые программы через `bash`. Перед созданием wrapper удаляется прежний файл или символическая ссылка, что исключает рекурсивный самовызов.

Closing keywords (`Closes`, `Fixes`, `Resolves`) запрещены в PR, если автоматическое закрытие может произойти до Release Gate и `PROCESS IMPROVEMENT REVIEW`. При преждевременном автоматическом закрытии ChatGPT обязан обнаружить событие и повторно открыть Issue.

## 9. Совместимость macOS

Целевая среда — штатный Bash 3.2 в macOS. Код не должен использовать возможности Bash 4+, включая `mapfile` и преобразование регистра `${var,,}`. Объявление локальных переменных и вычисление зависимых значений выполняются раздельно, чтобы режим `set -u` не приводил к ошибкам необъявленной переменной.

Программа поддерживает два расположения локальной копии:

- рабочая копия пользователя;
- управляемый клон в `$HOME/GitHub/<repository>`.

Если рабочая ветка уже существует на `origin`, программа создаёт локальную tracking-ветку вместо новой несвязанной ветки.

## 11. Версионирование

Первый стабильный выпуск: `GITHUB-ARTIFACT-PUBLISH-001 v1.0`. Изменения интерфейса карточек или контрольных алгоритмов требуют новой версии и записи в release notes.

## 12. Управление непрерывными улучшениями процесса

### 12.1. Обязательность

После каждой полной или частичной итерации жизненного цикла GitHub ChatGPT автоматически формирует `PROCESS IMPROVEMENT REVIEW`. Владелец не запускает этот анализ вручную и не обязан помнить его название, номер служебной Issue или момент выполнения.

### 12.2. Проверяемая последовательность

Review охватывает весь фактический маршрут:

`Issue → ветка → разработка → тесты → публикация → draft PR → независимая проверка → Owner/Merge Gate → merge → post-merge verification → release → PROCESS IMPROVEMENT REVIEW → закрытие Issue`.

Для каждого шага фиксируются действия владельца, ChatGPT, GitHub CLI или иной информационной системы и GitHub.

### 12.3. Обязанности ChatGPT

ChatGPT обязан:

1. восстановить фактически выполненную последовательность;
2. сравнить её с действующим регламентом;
3. проверить каждый шлюз и доказательство;
4. выявить ошибки, дублирование, пропуски и лишние ручные действия;
5. определить первопричины и влияние;
6. предложить улучшения и варианты автоматизации;
7. обновить реестр улучшений;
8. показать владельцу предложения для решения;
9. создать отдельную Issue на принятое изменение процесса, если требуется;
10. проверить эффективность внедрённого улучшения в следующей подходящей итерации.

### 12.4. Обязанности владельца

Владелец принимает управленческое решение по каждому предложению: `ACCEPTED`, `REJECTED`, `DEFERRED` либо изменение приоритета. Владелец не обязан самостоятельно вести реестр, формировать команды или помнить следующий системный шлюз.

### 12.5. Роль GitHub

GitHub хранит регламент, реестр, Issues, PR, commits и releases, связывая отклонение с изменением и результатом проверки эффективности.

### 12.6. Управление изменениями

Незадокументированное изменение процесса внутри предметной Issue запрещено. Правильный маршрут:

`обнаружено улучшение → зарегистрировано → решение владельца → отдельная Issue → разработка → тестирование → Owner/Merge Gate → merge → проверка эффективности`.

Немедленное исправление допускается только для критического дефекта, блокирующего текущую операцию. Оно всё равно регистрируется ретроспективно.

### 12.7. Завершение Issue

Issue считается полностью завершённой только при выполнении всех условий:

- опубликованный результат проверен в новом `main`;
- Release Gate пройден;
- `PROCESS IMPROVEMENT REVIEW` сформирован;
- отклонения и улучшения зарегистрированы;
- указано, требуется ли отдельная Issue;
- только после этого Issue закрыта как `completed`.
